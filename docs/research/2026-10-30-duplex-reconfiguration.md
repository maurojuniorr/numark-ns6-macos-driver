# Duplex reconfiguration observations, 2026-10-30

The diagnostic 1.0.5 on macOS 15.7.4 published one duplex NS6 device. In the 01:21 test the per-block trace included 128 blocks after the new client started: 126 contiguous transitions, no overlaps, and one 14,800-frame gap (~336 ms at 44.1 kHz). The CoreAudio log shows a device configuration cycle and a stop/start around the gap. This window does not establish that blocks never overlap at other times.

At 01:29:22 with the built-in microphone as system default input and NS6 output, the user heard the reset. Opera's helper requested microphone access at 01:29:22.414, before the CoreAudio configuration cycle beginning at 01:29:22.665 on BlackHole, followed by the built-in microphone, VB-Cable, and NS6. The NS6 configuration handler reported no change and I/O restarted around 01:29:23.130. At 01:30:06, with NS6 restored as default input, another Opera microphone request preceded a second NS6 configuration cycle and the user again heard a reset.

These observations show temporal correlation, not causation. A previous experiment on a different duplex build still glitched with Opera's microphone permission disabled. The default input alone does not explain the reset. The exact origin of the CoreAudio-wide reconfiguration remains unknown; no source-code change is justified solely by this observation. Preserve the Serato/VirtualDJ identity and ordered eight-read capture path during future work.

Chromium upstream macOS audio code enumerates input and output devices and filters private aggregate devices associated with VoiceProcessingIO. An older Chromium implementation notes input/output buffer sizing is shared and that VoiceProcessingIO creates an aggregate device. These are upstream implementation details, not evidence that the installed Opera build created such an aggregate. Searching the 01:29:21–01:29:24 CoreAudio log for aggregate/VoiceProcessingIO/VPIO returned no matching record. The observed processing-of-voice messages therefore cannot identify the initiating operation or prove creation of an aggregate. It did not write or record an audio file. Probe source: /private/tmp/ns6-coreaudio-probe.swift (temporary).

### Capture recovery and delay

The experimental 1.0.8 extended capture demand expiry from 250 ms to 1 s. The user reported that capture still glitched and had severe delay. In the log the USB reader continued while CoreAudio reconfigured input and the cumulative dropped capture frames increased, but the periodic counter does not attribute each drop to a particular reset. The ring holds 8192 stereo frames (about 186 ms at 44.1 kHz): when full, the producer drops new frames and preserves old ones. After a callback pause, normal real-time consumption may therefore carry a backlog forward instead of catching up. This mechanism can contribute up to the capacity of this ring; it does not establish the magnitude or origin of all user-reported delay, which can include the application. The 1.0.9 experiment restored the 250 ms expiry and is installed. A consumer-side backlog trim could reduce retained latency but discards captured audio; it cannot repair the missing interval while CoreAudio stops delivering callbacks. Validate against hardware and input recordings before adopting.

### Original kext timestamp pass

Read-only Ghidra decompilation of the original `NumarkNS6Audio` shows `bulkAudioInCompletion` calls `mach_absolute_time` and `AudioSM::AddTimeStamp` before resubmitting through `bulkInpEvent`. `TimeStampsBuffer::AddTimeStamp` stores pairs of time and cumulative position in a 1000-entry circular history using trylock; `AudioSM::updateZeroTimeStamp` obtains a time for a frame position and advances an epoch. These decompiled field interpretations are preliminary. Previous documented HAL analysis says `PGOSXDevice::onUSBProc` compares input availability with output position and invokes clients for complete blocks. The original HAL binary is no longer present at the path documented in the old investigation, so no new HAL decompilation was possible in this pass. None of this proves the vendor driver can prevent an application I/O pause caused by a system-wide CoreAudio reconfiguration.

### Public API research and limits

Apple documents separate input and output devices and aggregate devices, but does not document a driver property that vetoes another process enabling voice processing or prevents the host from suspending I/O during this reconfiguration. Apple's voice-processing description applies to applications choosing their processing API; it does not establish an Opera-specific switch. Sources: https://developer.apple.com/library/archive/documentation/MusicAudio/Conceptual/CoreAudioOverview/ARoadmaptoCommonTasks/ARoadmaptoCommonTasks.html and https://developer.apple.com/videos/play/wwdc2023/10235/. Avoid assuming Chromium or ChromeOS flags control macOS Opera. Driver-side per-client queues are a separate experiment and cannot force delivery during StopIO. A continuously running external recorder that reads NS6 USB outside the affected HAL path could potentially preserve samples, but existing OBS/TikTok HAL clients would still have a timestamp gap; end-to-end continuity and added latency would need separate proof.
